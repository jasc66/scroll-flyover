# scroll-flyover

Produces a landing page where **scroll drives a real 3D camera**: it flies from
outside a procedurally-built scene into its interior, then continues to the next
scene, continuously, with no visible cuts. Unlike AI-video approaches, nothing is
pre-rendered or generated by a paid service — **the browser's GPU renders the world
live**, every time, from code. This means:

- **Zero generation cost.** No per-clip billing, no credits, no API keys.
- **Infinitely re-editable.** Change a color, a shape, or the camera path and reload —
  no re-rendering a video chain.
- **Small payload.** A page is a few hundred KB of JS, not tens of MB of `.mp4`.
- **Genuinely interactive** if wanted (resize, reduced-motion, even a fallback for
  low-end GPUs) because it's a live scene, not a video.

The trade-off, stated plainly: procedural/primitive-based visuals read as **stylized
low-poly / geometric / abstract diorama**, not photoreal AI-generated art. Set that
expectation with the user up front (Step 1).

**What you generate:** N "island" scenes (each a self-contained Three.js group built
from primitives + code-generated textures) → one continuous camera spline that visits
them in order → a scroll-scrub engine that maps scroll position to a point (and
look-at target) along that spline.

Do not assume a frontend framework beyond "a browser." The engine is vanilla JS using
Three.js (MIT-licensed, loaded from a public CDN — free, no key). It builds its own
`<canvas>` and mounts into a container you give it, so it drops into plain HTML,
Next.js, Vue, a Python-served page, anything.

## Step 0 — Bootstrap

1. No CLIs, no API keys, no billing to check — this is the whole point. The only
   "dependency" is a Three.js build served from a CDN
   (`https://unpkg.com/three@0.169.0/build/three.module.js` — match
   `references/index-template.html`'s pinned version rather than floating on `latest`),
   or vendor it locally if the user wants a fully offline build — see Gotchas.
2. Confirm the target: a static HTML page, or a component embedded in an existing
   React/Vue/Next.js app. Both use the same engine; only the mount call differs
   (Step 6).
3. Skim `references/scene-recipes.md` before writing any scene code — it has the
   concrete primitive/material patterns per theme so you're not inventing geometry
   from scratch each time.

## Step 1 — Interview the user

Same spirit as any landing-page build: ask the subject openly, don't force it into a
pre-made list. Every choice below is deliberately narrow (2–3 options, never more) —
**Hick's law** (decision time rises with the number and complexity of choices) is why:
a longer menu doesn't make the result better, it just makes the interview slower.

1. **Subject** — "What should this world be about? A word or a sentence is fine —
   your business, a client's, or any idea." Capture the pitch and a name if they have
   one.
2. **Set the visual expectation honestly, once, up front:** this produces a stylized
   **low-poly / geometric diorama world** built from shapes and color, rendered live —
   not photoreal AI art. If the user actually wants photoreal, that needs an AI image/
   video pipeline (a different, paid, skill) — confirm they're fine with the
   procedural look before investing time in the interview.
3. **Palette** — 4–6 hex colors + one accent. This is the single biggest driver of how
   "designed" the result feels, since there's no photographic texture to lean on.
   Offer to propose a palette from the subject if the user doesn't have one.
4. **Shape language** (`AskUserQuestion`) — pick ONE, it becomes the shared visual
   grammar across every scene (this is what makes the world feel cohesive, the same
   role the "style preamble" plays in AI-image pipelines):
   - **Low-poly organic** — rounded islands, soft rock/hill silhouettes, faceted trees.
     Good for: nature, food, travel, wellness.
   - **Geometric / architectural** — cubes, cylinders, sharp-edged platforms, grid
     lines. Good for: tech, finance, logistics, real estate.
   - **Toy / rounded** — big soft-shadowed primitives, candy colors, bouncy proportions.
     Good for: kids' products, playful consumer brands.
5. **The journey (sections)** — 4–7 scenes the camera visits in order (**Miller's
   law**: working memory comfortably holds 7±2 items — past that, the journey stops
   feeling like a story and starts feeling like a list), derived from the
   subject's own value chain (same idea as the AI-video version: e.g. for a coffee
   brand — farm → roastery → café → cup). Each scene needs: a short description of
   what's IN it (2–4 sentences is enough — it becomes a recipe, not a prompt), an
   eyebrow, a headline, one line of body copy, 0–3 tag pills. Last scene is usually the
   hero product + CTA.
   **Peak-end rule (people judge an experience by its most intense moment and its
   ending, not the average of every moment)** — don't spread design effort evenly
   across all scenes. Pick ONE scene to be the deliberate "peak" (the most visually
   interesting build, e.g. the one with the most props or the photo panel from Step
   2.5) and make sure the LAST scene is genuinely the most polished, not an
   afterthought — those two are what the visitor will actually remember, everything
   else just needs to not be broken.
6. **Camera archetype** (`AskUserQuestion`) — the *structural* shape of the journey,
   and the single biggest differentiator between two builds. Six exist
   (`references/camera-archetypes.md`): island hop, continuous terrain, vertical
   descent, corridor/tunnel, orbit showcase, spiral ascent. **Don't list all six**
   (Hick's law) — infer 2–3 from the subject using that file's selection table, and
   deliberately include one non-obvious option alongside the safe one, saying which is
   which. The island hop is this genre's recognizable default; choosing something else
   is often the cheapest path to a build that doesn't look like the others.
7. **Camera feel** (`AskUserQuestion`) — how the camera behaves along whichever
   archetype was chosen:
   - **"Fly and swoop"** — the path banks through curves, more cinematic. Default for
     island hop, terrain, orbit, spiral.
   - **"Steady glide"** — level, calmer, no banking. **Required** for vertical descent
     and corridor (banking reads as tumbling there — see archetype compatibility notes).
8. **Performance target** (`AskUserQuestion`) — this replaces the AI-pipeline's
   "budget" question, since there's no money involved, only render cost:
   - **Rich** (shadows on, higher poly counts, particles) — fine for modern
     laptops/desktops; degrade for mobile (Step 7).
   - **Light** (flat shading, no shadows, low particle count) — safer default if the
     audience is mobile-heavy; still looks intentional, not broken.
9. **Their own photos, if any** (`AskUserQuestion`) — "Do you have real photos you'd
   like to feature (a product shot, a team photo, a logo)?" This is separate from Step
   1.2's "no AI photoreal" expectation-setting — a user's own uploaded image is free
   and welcome, only AI-*generated* imagery is out of scope. If yes:
   - Ask which 1–2 moments they should anchor (usually the hero/last scene and/or one
     "meet the team/product" scene) — never all scenes; see Step 2.5 for why.
   - Get the actual image file(s) (or a path/URL they control) before Step 2.5.
   - If no, skip Step 2.5 entirely and the world stays fully procedural.

Nothing here blocks on external services, so there's no "wait for a render" step —
move straight to building once the interview is done.

## Step 2 — Build each scene as a self-contained group

Each scene is a `THREE.Group` positioned along the world axis (scenes laid out roughly
in a line or gentle arc in 3D space — the camera path visits them, Step 3). Build every
scene from the **same recipe family** chosen in Step 1.4 so the world reads as one
place. See `references/scene-recipes.md` for concrete, copy-pasteable primitive
patterns (islands, buildings, foliage, water, props) — don't invent new geometry
patterns per scene; reuse the same 4–6 primitive "vocabulary" pieces with different
counts/colors/scale so scenes feel like siblings.

Rules that keep it cohesive and fast:
- **One base platform shape per scene** (a squat cylinder, a rounded box, or an
  irregular low-poly blob) sized similarly across scenes — this is the "island" the
  camera dives into, same conceptual role as the diorama still in an AI pipeline.
- **Reuse materials.** Create a small palette of `MeshStandardMaterial`/
  `MeshLambertMaterial` instances up front (from Step 1.3's hex palette) and assign
  them across scenes rather than allocating new materials per mesh — cheaper and
  visually consistent.
- **No AI-generated or third-party-fetched images, ever.** Skies, ground gradients,
  and "grain" all come from a tiny canvas-texture generator (recipe in
  scene-recipes.md) — a `<canvas>` you draw a gradient/noise into at runtime and feed
  to `THREE.CanvasTexture`. This is the direct replacement for "generate a still with
  an image model": it's code, it's instant, and it costs nothing. **The one exception
  is the user's own photos**, opted into at Step 1.9 — those are loaded locally like
  any other project asset, not generated or fetched from a paid service, and are
  covered separately in Step 2.5. Don't confuse the two: fetching a stock photo or
  calling an image model is still out of scope even for "just one hero prop."
- **Keep polycounts modest.** Prefer `IcosahedronGeometry(r, 0)` / `(r, 1)` (low
  detail) over high-subdivision spheres; instance repeated props
  (`InstancedMesh`) instead of cloning meshes when a scene needs many similar objects
  (a forest, a crowd of boxes).
- **Fog per scene is optional but cheap** and does a lot of the "atmosphere" work a
  photoreal render would otherwise carry — set `scene.fog` once globally using the
  palette's darkest color, not per scene.
- **NEVER call `Math.random()` in a scene builder.** Every `build()` receives a seeded
  `rng` in its options argument — use it for all prop placement, scale, and rotation
  jitter. With `Math.random()`, a brand's page renders differently on every reload and
  on every visitor's screen: the client can't approve a layout they can't reproduce,
  screenshots never match the live page, and a "fix this one overlapping prop" request
  is unactionable. The seed lives in `config.seed`; changing it reshuffles the whole
  world on purpose, and each scene gets its own derived stream so editing scene 3
  doesn't move scene 1's props. This is not a nicety — it's what makes the build a
  deliverable rather than a slot machine.
- **Reach for real materials before adding more geometry.** Flat-colored primitives are
  what make procedural 3D read as a tutorial demo. `references/materials.md` has
  palette-derived marble/wood/water/rim-glow/sky-dome generators — all canvas or
  20-line shaders, all free, all seeded. Texturing three existing props usually beats
  adding ten more untextured ones, and costs far less GPU. Respect that file's
  per-tier budget table.

## Step 2.5 — Optional: incorporating the user's own photos

Skip this step entirely if Step 1.9 came back "no photos" — the world stays fully
procedural and nothing here applies.

If the user opted in, their photo(s) become **textures** loaded locally with
`THREE.TextureLoader`, exactly like any other web asset — no API, no generation call,
no cost. See `references/scene-recipes.md` §8 for the copy-pasteable loader/panel/prop
code. The design discipline that keeps this from clashing with the procedural world:

- **A photo is a deliberate accent, not the new default.** Use it in the 1–2 scenes
  the user named at Step 1.9 — usually the hero/last scene (a real product shot) and/or
  one "meet the team" scene — never scatter photos across every scene. Every other
  scene stays procedural. The contrast (stylized world, one real photo) is what makes
  the photo read as intentional rather than like a stock image pasted into a diagram.
  This isn't just taste: it's the **Von Restorff effect** (an item that differs from
  its surroundings is disproportionately remembered) — the photo only stands out
  *because* everything around it is procedural. Photo-in-every-scene erases the
  contrast that makes any single photo memorable in the first place.
- **Frame it like a designed object, not a floating rectangle.** Back the photo plane
  with a slightly larger plane in the palette's accent color (a "mat"/frame effect,
  recipe §8) so it reads as a deliberately placed artifact in the diorama, not a UI
  screenshot floating in 3D space.
- **Preserve the photo's real aspect ratio.** Read `texture.image.width/height` once
  loaded and size the plane geometry to match — a stretched or squashed photo is the
  single fastest way to make an otherwise good scene look broken.
- **Downscale before use.** A phone photo can be 4000px+ on a side; that's wasted GPU
  memory for a prop that might render at 300px on screen. Resize to a sane max
  dimension (≈1024px) before handing it to `TextureLoader` — either ask the user for a
  pre-resized file, or resize with a `<canvas>` at load time (recipe §8 shows both).
- **Color space matters.** Set `texture.colorSpace = THREE.SRGBColorSpace` (modern
  Three.js) on any loaded photo, or it renders washed-out/flat against the
  `MeshStandardMaterial` lighting the rest of the scene uses.
- **Handle load failure gracefully.** `TextureLoader.load` takes an `onError` callback
  — fall back to a flat accent-colored panel (not a broken/blank texture) if the file
  path is wrong or the image fails to decode, so one bad asset doesn't blank out the
  whole scene.

This step is the one deliberate, narrow exception to "everything is procedural" — keep
it narrow. If the interview reveals the user actually wants many/most scenes built
from photos, that's a different kind of site (a photo gallery/portfolio scroller, not
a diorama world) — say so and confirm before restructuring the whole build around it.

## Step 3 — The camera path (this is the seam rule — read before building the spline)

The entire "no cuts, one continuous flight" illusion lives in **one spline**:
`THREE.CatmullRomCurve3` built from control points that pass near/through each
scene's platform, plus extra control points that dip toward the platform's interior
(the "dive") between each pair of scenes. This is simpler and more robust than the
AI-video seam problem — there's no frame-matching to get wrong, because there's no
video: the camera is one continuous mathematical curve, so continuity is automatic.

Concretely, for N scenes:

1. Lay out scene anchor points `P_0 … P_{N-1}` in world space (a gentle arc or line,
   spaced so consecutive scenes don't overlap — recipe in `references/camera-path.md`).
2. For each `P_i`, add THREE points to the curve: an **approach** point (outside/above
   the scene, wide view), a **dive** point (inside/close, near the focal prop), and a
   **depart** point (lifted back out, angled toward `P_{i+1}`). This mirrors the AI
   pipeline's dive-clip + connector-clip structure, but as one curve instead of two
   separate renders.
3. Build `new THREE.CatmullRomCurve3(points, false, 'catmullrom', 0.5)` once. Map
   scroll progress `t ∈ [0,1]` to `curve.getPointAt(t)` for camera position and
   `curve.getPointAt(min(t + lookAhead, 1))` as the look-at target (a small
   `lookAhead`, e.g. 0.01–0.02, keeps the camera oriented into the direction of travel
   — this the direct analog of the "forward drift" rule in the AI pipeline, and here
   it's free/automatic instead of something you have to prompt for).
4. **Per-scene dwell** — give the segment of the curve near each scene's dive point
   more of the `[0,1]` range than the transit segments, so scroll feels like it lingers
   in the interesting parts. Do this by using a non-uniform re-parameterization (a
   small easing lookup table, detailed in `references/camera-path.md`) rather than by
   spacing control points unevenly (uneven spacing distorts speed weirdly on a
   Catmull-Rom curve).
5. **Camera roll/bank** (only if "fly and swoop" was chosen, Step 1.7) — derive a bank
   angle from the curve's curvature at each point (`curve.getTangentAt`) rather than
   hand-authoring rotations; this keeps banking physically plausible and free of
   per-scene tuning. "Steady glide" skips this — camera stays level, `up = (0,1,0)`
   always.

Because this is one continuous curve, there is no equivalent of the AI-pipeline's
"architecture A vs B" choice, no seam pop, and no risk of the camera visually
reversing — reversal is only a problem when you're stitching separately-rendered
clips. Scrolling up simply walks `t` backward along the same curve, which is correct
by construction.

## Step 4 — Render setup: the difference between "tutorial" and "designed"

**Read `references/visual-fidelity.md` before writing any lighting code.** This is the
step most responsible for a build looking basic, and the failure is never polygon
count — it's render setup. Three things are mandatory on every build, including the
Light tier, because they cost almost nothing:

1. **ACES Filmic tone mapping** (`renderer.toneMapping`) — raw WebGL clips highlights
   to flat white, which is most of why untuned scenes look like plastic. Two lines.
2. **A procedurally-generated environment map** via `PMREMGenerator` (no HDRI file, no
   download). Without one, `MeshStandardMaterial`'s roughness/metalness channels do
   nothing and every prop reads as matte cardboard. This is the single most common
   cause of "it looks basic."
3. **Materials that actually use it** — `roughness ≤ 0.5`, `metalness ≥ 0.1` on hero
   props. `scene-recipes.md`'s defaults (0.85/0.02) are deliberately safe and
   deliberately dull; override them once the env map is in place.

Then the lighting itself:

- One `THREE.HemisphereLight` (sky/ground from the palette) + one shadow-casting
  `DirectionalLight` for the whole scene graph — not per island. Tune the shadow
  frustum and set `PCFSoftShadowMap` (visual-fidelity.md §5); untuned shadows are
  worse than none.
- `scene.background` from a gradient sky dome (materials.md §5), with `scene.fog`
  matching the dome's lower stop — a mismatched fog color is an instant tell.
- **Bloom** (`UnrealBloomPass`, from Three.js's own addons) plus exactly ONE emissive
  prop in the peak scene. Rich tier only — it's a full-screen pass costing ~1.3–1.6×
  frame time, and a cinematic build at 20fps is worse than a clean one at 60.
- Drifting particles only if the Rich tier is on and the scene still feels empty
  *after* the above — particles are the weakest fidelity lever, not the first reach.

**Silhouette matters as much as shading.** Perfectly sharp 90° box corners are the
other half of the "primitive" read. Bevel everything (`RoundedBoxGeometry`), and make
sure at least one shape per build is NOT a Three.js primitive — `ExtrudeGeometry` from
a custom 2D profile, or `LatheGeometry` from a spun curve. A world assembled purely
from the primitive list looks assembled; one custom silhouette changes that
(visual-fidelity.md §3).

Run the fidelity checklist at the end of `references/visual-fidelity.md` before showing
any build to a client.

## Step 5 — Copy overlay and progress rail

Section copy (eyebrow/title/body/tags/CTA) is plain HTML/CSS pinned over the canvas,
not baked into the 3D scene — exactly like the AI-video engine's approach, and for the
same reason: text needs to stay crisp and accessible regardless of what the camera is
doing. Fade each section's copy in as scroll enters its dwell range (Step 3.4) and out
as it leaves; `references/scrub-engine.js` includes this wiring already.

**Route rail (Zeigarnik effect — unfinished sequences pull attention more than finished
ones).** A visitor who can't see how much world is left has no reason to keep scrolling
past the first scene. Pin a small vertical row of dots (one per scene) to one edge of
the viewport; fill/highlight the dot whose dwell range contains the current scroll `t`,
and leave the rest as outlines. This costs a handful of `<div>`s and one class toggle
per scroll tick — `references/scrub-engine.js` includes it — but it's the difference
between "infinite scroll with no sense of progress" and a journey the visitor can see
themselves completing.

**Tap targets (Fitts's law — acquisition time rises with distance and falls with
target size).** Any interactive element pinned over the canvas — the CTA button, the
route-rail dots if made clickable — needs a real hit area of at least 44×44px on
touch, even if the visible dot/icon is smaller (pad the tappable wrapper, don't just
enlarge the graphic). This matters more here than on a normal page because the
visitor's thumb is also the thing driving scroll — a near-miss tap is more disruptive
mid-flight than in a static layout.

## Step 6 — Assemble the page

Copy `references/scrub-engine.js` and `references/index-template.html` into the
user's project (or adapt the mount call into their framework — it's one function).
**Exception:** if the host project needs i18n or otherwise must render copy through
its own component system, don't adapt this engine's DOM-baked copy — reimplement the
mount function in the host's language, keep only the DOM-independent parts (seeded
RNG, curve, easing) from this file, and drive the host's own components from a
headless progress callback instead. See `references/production-lessons.md`. Config
shape:

```js
mountScrollFlyover(document.getElementById('world'), {
  palette: { colors: ['#2b6777','#52ab98','#c8d8e4','#f2f2f2'], accent:'#e8a33d' },
  shapeLanguage: 'lowpoly',        // 'lowpoly' | 'geometric' | 'toy'
  cameraFeel: 'swoop',             // 'swoop' | 'glide'
  performance: 'rich',             // 'rich' | 'light'
  seed: 20260906,                  // any integer — makes the build reproducible (Step 2)
  layout: layoutSpiral,            // optional archetype from camera-archetypes.md; omit for island hop
  photos: { hero: 'assets/product-hero.jpg', team: 'assets/team.jpg' }, // optional, Step 2.5 — omit entirely if no photos
  scenes: [
    { id:'farm', build: buildFarmScene,     // a function returning a THREE.Group — see scene-recipes.md
      eyebrow:'From the hills', title:'It starts on the farm.',
      body:'…', tags:['Single-origin'] },
    // …one per scene; last may carry a `cta`
  ],
});
```

Each scene's `build` function is user (or Claude)-authored code following the recipes
in `references/scene-recipes.md` — this is the direct replacement for an AI image
prompt: instead of describing the scene in English for a model, you describe it in
Three.js primitives. The full signature is `build(materials, textures, options)`:

- `materials` — the shared palette-derived material array (Step 2).
- `textures` — loaded user photos, when `photos` is configured (Step 2.5); the engine
  loads each entry once with `THREE.TextureLoader`, so only the scene(s) that want a
  photo reach into it (`references/scene-recipes.md` §8).
- `options` — `{ shapeLanguage, performance, rng, palette }`. **`rng` is the seeded
  random source and the only one a builder may use** (Step 2). `palette` is passed so
  builders can generate palette-derived materials (`references/materials.md`).

A scene group may set `userData.tick = (elapsed) => {…}`; the engine calls it every
frame for material animations like scrolling water, and skips it under
`prefers-reduced-motion`.

The engine also emits a **visually-hidden, crawlable HTML block** containing every
scene's eyebrow/title/body/tags as real semantic markup. A WebGL canvas is invisible
to search engines, link-preview scrapers, and screen readers in browse mode; this
block costs nothing at runtime and is why a flyover page can rank and be shared at
all. Don't strip it when adapting the engine into a framework.

For a framework embed (React/Vue/Next.js): call `mountScrollFlyover` inside a
`useEffect`/`onMounted` against a ref'd container div, and call the returned
`dispose()` function on unmount to free the renderer/geometries.

## Step 7 — Performance and mobile

Since rendering happens live on the visitor's device (unlike pre-rendered video, which
is equally cheap to play on any device), this is the one place a free approach has to
work harder than the AI-video approach:

- **Cap pixel ratio**: `renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2))`
  — retina displays otherwise silently 4x the fragment cost.
- **Reduce on coarse pointer / narrow viewport**: on mobile, force `performance:
  'light'` behavior regardless of the desktop setting picked in Step 1.8 — halve
  particle counts, disable shadows, drop geometry detail level by one step
  (`IcosahedronGeometry(r,1)` → `(r,0)`).
- **`prefers-reduced-motion`**: stop the scroll-driven camera animation loop and jump
  directly to each section's dwell-center point on scroll, no continuous flight — same
  accessibility behavior the AI-video engine gives for free.
- **Pause the render loop when the tab/section is off-screen** (`IntersectionObserver`
  on the container, `document.visibilityState`) — a live scene keeps costing GPU/battery
  even when unseen, unlike a paused video.
- **WebGL context loss**: listen for `webglcontextlost` and show the poster fallback
  (a single static canvas-drawn frame captured on first render) rather than a blank
  page — low-end/overloaded GPUs can drop the context.

## Step 8 — QA

- Scroll from top to bottom and back slowly, then flick fast: the camera must track
  smoothly both directions with no stutter or pop-in (there's no seam to break, but
  frame drops from too many draw calls will feel similar — check the browser's FPS
  meter, target ≥50fps desktop / ≥30fps mobile at the chosen performance tier).
- Resize the window / rotate a phone: the world must not distort (update camera aspect
  + renderer size on `resize`, debounced).
- Confirm copy timing: each section's text should be legible for a comfortable window
  around its dwell center, not a instant flash.
- Test `prefers-reduced-motion` (OS setting) — page should still be fully readable
  without the animation.
- Throttle CPU 4–6× in devtools and confirm the "Light" tier still holds together.
- **Run the fidelity checklist** at the end of `references/visual-fidelity.md`. A build
  failing two or more of its items is what "it looks basic" means in practice.
- **Reload the page three times and compare screenshots — they must be pixel-identical.**
  Any difference means a builder is using `Math.random()` instead of the seeded `rng`
  (Step 2). This is the check that turns the build into something a client can sign off
  on. `references/qa-reproducibility.mjs` automates this against a served URL (`node
  qa-reproducibility.mjs <url>`, needs `playwright`) — it also confirms a real WebGL2
  scene rendered rather than the static fallback, which is what makes this check
  trustworthy headless (see `references/gotchas.md`, "Reproducibility and QA").
- **View source / disable JS** and confirm the crawlable copy block is present with
  every scene's headline and body text. Run the URL through a link-preview or
  rich-results checker: if it comes back empty, the block was stripped during a
  framework adaptation.
- Grep the finished build for `Math.random` (should be zero) and confirm each canvas
  texture generator is called once, not per scene.
- **Run an accessibility audit on the HTML overlay** — if an `accessibility-reviewer`
  agent (or equivalent) is available, invoke it against the finished page. Scope it
  correctly: the WebGL canvas itself is not auditable (it's a rendered picture, not
  semantic content) and is out of scope by design — the actual accessibility surface
  of a flyover build is everything layered on top of it: the copy overlay (heading
  structure, color contrast per Step 4/`production-lessons.md`'s 3D-vs-HTML color
  note), the CTA and route-rail buttons (44×44px targets, `aria-label`s, real
  `<button>` elements — Step 5), the crawlable SEO block (semantic tags, not just
  present but structured as real headings/paragraphs — this Step), and the
  `prefers-reduced-motion` fallback (content fully readable, not just animation-free).
  Tell the agent explicitly to skip the canvas and focus there; feeding it a page
  that's "mostly a `<canvas>`" without that scoping wastes the pass on a false
  negative. Treat its findings the same as any other QA failure — fix before calling
  the build done, don't defer "for later."

- **Interaction and overlay** — unreachable route-rail dots, clicks hitting the wrong

## Deliberate uniqueness (this is the part usability laws don't cover)

The single biggest risk to this skill's output isn't a usability bug — it's **visual
sameness**. Every build reuses the same three shape-language vocabularies (Step 1.4)
and the same primitive toolbox (scene-recipes.md), so left on autopilot, two builds
with different palettes can still look like siblings of the same Three.js tutorial
demo. Fix this at the interview, not after:

1. **Push Step 1.1 past the generic category.** "A bakery" produces generic
   bread-loaf primitives. The one physical/sensory detail that makes *this* bakery
   different from every other bakery — a wood-fired oven visible from the street, a
   mural on one wall, a specific ritual in how the product is made — is what a
   template can't produce. If the user's answer stays generic, ask one follow-up
   ("what's the one thing about this that a stock description would miss?") before
   moving on.
2. **Turn that detail into a signature motif, invented for this build only.** One
   recurring geometric idea that repeats across every scene the same way the shape
   vocabulary does — but that comes from the answer in (1), not from a preset list.
   E.g. "every scene has one oversized/glowing prop pulled from the real detail" or
   "every platform shows a visible seam where two accent colors meet." This is what
   actually varies build-to-build; the shape-language choice (lowpoly/geometric/toy)
   alone does not.
3. **Break exactly one convention on purpose.** Pick ONE: an unusual camera height, a
   jarring accent color instead of a harmonious one, a non-arc scene layout, uneven
   scene spacing. State the choice to the user as a deliberate departure, not a
   default. One broken convention reads as style; breaking several at once reads as a
   bug — this is Prägnanz applying to the departure itself, see
   `references/ux-principles.md`.

This isn't a new pipeline step to run in sequence — it's a lens to hold while doing
Step 1.1 and Step 1.4. Spend the extra two interview questions here; it's cheaper than
discovering at Step 8 that the build looks like a generic demo.
